# 07. 스트리밍 복제 · 장애 전환 실습 — 비동기 vs 동기, "성공이라고 답한 쓰기"는 살아남는가

> 실습일 2026-11-09 · 환경: `ops-lab/replication/docker-compose.yml`(PostgreSQL 16.15 primary 1 + standby 1, 같은 Docker 호스트)
> 운영(Supabase)과 무관 · 표기: **[측정]** 실제 실행 · **[추정]** 미검증

## 1. 질문과 "정상"의 정의

| 질문 | 측정 방법 |
|---|---|
| 쓰기 직후 standby에서 읽으면 새 값이 보이는가 | primary에 UPDATE(커밋 응답 받음) → 곧바로 standby에서 SELECT, 300회 |
| 복제 모드가 쓰기 성능을 얼마나 깎는가 | 8개 워커가 15초간 1건씩 INSERT, 처리량·p50/p95/p99 |
| primary가 갑자기 죽으면 "커밋 성공" 응답을 받은 쓰기가 남는가 | 쓰기 도중 `docker kill -s KILL` → standby 승격 → 클라이언트가 기록한 성공 목록과 새 primary의 행 비교 |

**정상(동기 복제의 약속)**: 클라이언트가 성공 응답을 받은 커밋은 승격된 standby에 **하나도 빠짐없이** 있어야 한다.

## 2. 구성
- standby는 처음 뜰 때 `pg_basebackup -R -C -S standby1`로 복제본을 만든다(`-R`: 복제 접속 설정 자동 작성, `-C -S`: 복제 슬롯 —
  standby가 잠시 끊겨도 primary가 필요한 WAL을 지우지 않게). 이후 WAL을 실시간으로 받아 재생하며 읽기 질의를 받는다(hot standby).
- 복제 전용 역할 `replicator`는 REPLICATION 권한만 있다(테이블 읽기·쓰기 불가 — 04 §5의 최소 권한과 같은 원칙).
- 동기 여부는 primary의 `synchronous_standby_names`·`synchronous_commit`으로 실습 중에 바꾼다.
- 측정 도구 `ops-lab/scripts/replicationProbe.ts`: 커밋 성공 응답을 받은 쓰기만 `acked`로 기록(백엔드 Prisma 사용, 새 패키지 없음).

초기 검증 [측정]: 마이그레이션 12개 + 대량 데이터(게시물 2만 건)를 primary에 넣은 뒤 정합성 점검(행 수·체크섬·규칙·스키마 객체)이
standby와 일치. standby에서의 쓰기는 `cannot execute UPDATE in a read-only transaction`으로 거부.

## 3. 1부 — 복제 모드별 성능과 읽기 일관성 [측정]

| 모드 | 설정 | 처리량 | p50 | p95 | p99 | 최대 복제 지연 | **standby 옛 값 읽기** |
|---|---|---|---|---|---|---|---|
| 비동기 | 기본 | 3,557 tps | 1.72ms | 2.83ms | 13.1ms | 1,608B · 2.8ms | **82.3%** (300회 중 247회) |
| 동기 `on` | 커밋이 standby **디스크 기록(flush)**까지 대기 | 3,138 tps | 2.39ms | 3.15ms | 7.25ms | 1,096B · 2.5ms | 0% |
| 동기 `remote_apply` | 커밋이 standby **재생(apply)**까지 대기 | 3,318 tps | 2.20ms | 2.87ms | 4.02ms | 1,168B · 9.5ms | 0% |

- **비동기에서 쓰기 직후 standby를 읽으면 82%가 옛 값**이다(새 값이 보이기까지 최대 2.5ms). 지연은 짧지만 "쓰고 바로 읽기"에는 충분히 길다.
  → 백엔드가 읽기를 복제본으로 보내면 "방금 쓴 글이 목록에 없다" 같은 버그가 난다. 쓰기 직후의 읽기(read-your-writes)는 primary로 보내거나
  `remote_apply`를 써야 한다.
- `synchronous_commit = on`은 standby의 **디스크 기록**까지만 기다리고 **재생**은 기다리지 않는다 — 옛 값 읽기가 원리상 가능하다.
  이번 측정에서 0%였던 건 재생이 빨랐기 때문이다 [추정: 부하가 크면 나타날 수 있음]. 읽기 일관성이 필요하면 `remote_apply`가 보장이다.
- 동기 비용이 7~12%로 작은 것은 primary·standby가 **같은 호스트**라 왕복 지연이 거의 없어서다. 실제로 다른 데이터센터에 두면
  커밋마다 그 왕복 시간이 더해진다 [추정].

## 4. 2부 — 쓰기 도중 primary 즉사 → standby 승격 [측정]

| 모드 | 실행 | 클라이언트가 받은 커밋 응답 | **응답 받았는데 새 primary에 없음(유실)** | 응답 없이 반영됨 | 승격 | 쓰기 가능까지 |
|---|---|---|---|---|---|---|
| 비동기 | 10회 | 회당 약 1.1~2.1만 건 | **2회에서 각 4건**(나머지 8회 0건) | 0 | 0.72~0.84초 | 0.94~1.03초 |
| 동기 `on` | 3회 | 회당 약 1.3만 건 | **0건(3/3)** | 2~3건 | 0.78~0.84초 | 1.03~1.08초 |

- **비동기 복제는 "성공"이라고 답한 쓰기를 잃을 수 있다**(10회 중 2회). primary는 로컬 커밋 직후 응답하고 WAL은 나중에 보내므로,
  그 사이에 죽으면 standby에 없는 커밋이 생긴다. 이번 유실이 작은 건 복제 지연이 1ms 미만이었기 때문이다 — 지연이 크면 유실도 커진다.
- **동기 복제는 유실이 없었다**. 대신 **"응답 없이 반영된" 커밋**(standby에는 있는데 primary가 응답 전에 죽어 클라이언트는 실패로 앎)이 매번 2~3건 생겼다.
  클라이언트가 실패로 알고 **재시도하면 같은 쓰기가 두 번** 들어간다 → 쓰기 API는 멱등해야 한다(1차 작업의 담기 멱등 처리 · 유니크 제약이 바로 이 상황의 방어선).
- 승격은 `SELECT pg_promote()` 수동 실행 기준 약 1초. 장애 **감지** 시간은 포함하지 않았다 — 자동 감지·승격은 Patroni 같은 도구의 역할이고,
  감지 기준(타임아웃)을 너무 짧게 잡으면 네트워크 순단에도 승격되어 primary가 둘이 되는(split-brain) 위험이 있다.

## 5. 정리 — 어떤 모드를 언제

| 요구 | 선택 | 대가 |
|---|---|---|
| 성공 응답 받은 쓰기는 절대 잃지 않음(결제·재고) | 동기 `on` 이상 | 커밋 지연 +왕복 시간, standby가 죽으면 **쓰기가 멈춤**(standby 2대 이상 + `ANY 1 (...)`로 완화) |
| 쓰기 직후 복제본 읽기 일관성 | `remote_apply` 또는 해당 읽기를 primary로 | 커밋 지연 +재생 시간 |
| 처리량 우선, 장애 시 직전 몇 건 손실 허용(이 서비스의 둘러보기 등) | 비동기 | 장애 전환 시 수 건~수 초 분량 유실 가능 |

이 서비스에 적용한다면: 담기·후기 쓰기는 이미 멱등(유니크 제약 + P2002 해석)이라 동기 복제의 "응답 없이 반영" 재시도에 안전하다.
읽기 복제본을 도입할 경우 쓰기 직후 화면(담기 직후 보관함, 후기 작성 직후 목록)은 primary에서 읽어야 한다.

## 6. 재현 방법

```bash
bash ops-lab/scripts/replication-drill.sh                                  # 1부 + 2부(비동기·동기 각 3회)
PARTS=2 FAILOVER_MODES=async REPS=7 bash ops-lab/scripts/replication-drill.sh
docker compose -f ops-lab/replication/docker-compose.yml down -v
```

## 7. 남은 한계
- primary·standby가 같은 호스트(네트워크 지연 ≈ 0) — 실제 지연 환경의 성능·유실 규모는 [추정].
- 장애 감지·자동 승격(Patroni 등), 옛 primary를 새 primary의 standby로 되돌리는 `pg_rewind`는 실습하지 않았다.
- standby 1대 구성이라 동기 모드에서 standby가 죽으면 쓰기가 멈추는 상황은 측정하지 않았다.
- 표본: 비동기 장애 전환 10회, 동기 3회.
