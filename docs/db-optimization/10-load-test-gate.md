# 10. k6 부하 테스트 + PR 성능 게이트 — "게이트가 실제로 회귀를 잡는가"를 회귀를 주입해 검증

> 실습일 2026-11-09 · 도구: k6 0.54, PostgreSQL 16(로컬 테스트 컨테이너), Node 22/24 · 데이터: `seed-large.sql` 합성 데이터
> (setseed 고정, 실제 사용자 데이터 없음) · 측정 환경: Windows 11 개발 PC + Docker Desktop(k6는 컨테이너, 서버는 호스트)
> · 표기: **[측정]** · **[추정]** · **[미검증]**

## 1. 목표

PR마다 백엔드 성능이 나빠졌는지 자동으로 판정한다. "부하 스크립트가 돈다"에서 멈추지 않고 다음을 확인한다.
1. **오탐이 없는가** — 같은 코드끼리 비교(A/A)해도 통과하는가. 기준값은 이 잡음 폭을 보고 정한다.
2. **회귀를 잡는가** — 인덱스 삭제·캐시 제거 같은 회귀를 일부러 넣었을 때 실패하는가.

## 2. 구성

| 파일 | 역할 |
|---|---|
| `backend/scripts/load/api.k6.js` | 부하 시나리오. 엔드포인트별 `ep` 태그, 앞 10초 워밍업 분리, 엔드포인트별 p95 < 800ms 절대 기준 |
| `backend/scripts/load/perf-gate.sh` | base·head 각각 **자기 커밋의** 마이그레이션·시드로 DB 생성 → 빌드·기동 → 라운드마다 순서를 뒤집어(B H / H B / B H) k6 실행 |
| `backend/scripts/load/compare.mjs` | 라운드 중앙값 p95 비교·판정, 표를 Actions 요약에 출력 |
| `.github/workflows/perf.yml` | `backend/**`가 바뀐 PR에서 실행. PR 대상 커밋을 별도 작업 트리로 꺼내 base로 쓴다. 수동 실행 시 A/A 옵션 |

**설계 결정**
- **기준값을 저장하지 않고 같은 러너에서 base·head를 번갈아 잰다.** 같은 코드·같은 설정도 실행마다 절대값이 달랐다.
  feed_popular p95가 한 실행에서는 11.1ms, 다른 실행에서는 7.9ms였다 [측정, §6]. 어제 저장한 값과 비교하면 러너 차이가 회귀처럼 보인다.
- **도착률 고정(open model, `constant-arrival-rate`).** 초당 약 52회 반복, 약 70 요청/초로 구성했다.
  - 둘러보기 20, 검색 8, 상세 10, 장소 후기 10, 담기→취소 4.
  - VU 수를 고정하면 서버가 느려질 때 요청도 줄어 지연이 가려진다(coordinated omission).
  - 요청을 못 보낸 횟수(`dropped_iterations`)는 포화 신호로 따로 판정한다.
- **판정은 비율과 절댓값을 둘 다 넘어야 회귀**로 본다(+25% 그리고 +5ms). 근거는 §3이다.
- 담기 요청은 시드 사용자 이름으로 JWT를 직접 서명한다(합성 사용자라 비밀번호가 없음). 게이트 전용 일회용 시크릿이다.
- 안전장치: DB를 DROP하므로 `PG_URL`이 로컬 호스트가 아니면 시작하지 않는다. k6의 대상 URL도 로컬만 허용한다.

## 3. A/A — 같은 코드끼리 비교한 잡음 폭 [측정]

| 규모 | 최대 차이 | 결과 |
|---|---|---|
| scale 0.1(게시물 1만) | +11%(feed_recent, 0.5ms) | 통과 |
| scale 1(게시물 10만) | **+27%(feed_popular, 5.7 → 7.3ms, +1.6ms)** | 통과 — 비율만 봤다면 **오탐**, +5ms 하한이 막음 |

- 빠른 엔드포인트(5ms대)는 1~2ms만 흔들려도 수십 %가 된다. 그래서 비율만으로는 판정할 수 없다.
- 반대로 절댓값만 쓰면 느린 엔드포인트(검색 150~240ms)의 25% 회귀를 놓친다. 그래서 둘 다 넘어야 회귀로 본다.
- A/A는 규모별 1회씩만 돌렸다. 기준을 다시 정할 때는 워크플로를 수동 실행(`aa: true`)해 CI 러너에서 다시 잰다.

## 4. 회귀 주입 ① trigram 인덱스 삭제 — 게이트가 두 번 놓쳤다 [측정]

head에만 `DROP INDEX "Post_searchText_idx"` 마이그레이션을 넣고 돌렸다.

| 시도 | 검색 p95 base → head | 판정 | 왜 |
|---|---|---|---|
| scale 0.1, 검색 하나로 집계 | 32.4 → 30.9ms | **놓침** | 1만 건에서는 결과 있는 검색어가 원래 순차 스캔이고, 인덱스는 결과 없는 검색어에만 쓰였다(EXPLAIN 확인) |
| scale 1, 검색 하나로 집계 | 228.3 → 265.2ms (+16%) | **놓침** | 느려진 건 드문 검색어(검색의 약 8%)뿐이다. 실행계획이 다른 두 부류를 한 p95에 섞으니 묻혔다 |
| scale 1, **흔한/드문 검색어 분리 집계** | 드문 검색어 **6.5 → 288.8ms (44배)** | **잡음** | |

**고친 것**
- 게이트 데이터를 **scale 1**로 정했다. 시드 39~47초, 작으면 실행계획이 운영과 달라진다.
- 검색을 **실행계획이 다른 부류별로 따로 집계**한다.
  - `search_common`: 결과가 많아 count가 순차 스캔.
  - `search_rare`: 오타나 없는 말이라 인덱스가 있으면 즉시 끝난다.

## 5. 예상 밖의 발견 — 인덱스를 지웠더니 흔한 검색어가 37% 빨라졌다

위 실험에서 흔한 검색어 p95는 오히려 **230.9 → 146.2ms**가 됐다. A/A에서 같은 지표의 차이는 -1%였으므로 잡음이 아니다.

**가설 1. GIN pending list → 기각**
- 담기 트리거의 `Post.saves` UPDATE는 HOT이 안 된다. 그래서 GIN의 pending list가 쌓이고, 검색이 이 목록을 훑는다는 가설이었다.
- 부하 뒤 pending list는 279건이었다.
- 통제 실험(UPDATE 300건으로 pending 241건을 만듦)에서 같은 검색은 **30.3ms**, pending list를 정리한 뒤에는 **26.2ms**였다.
- 4ms 차이라 주원인이 아니다.

**가설 2. prepared statement의 generic plan → 확인 [측정]**
- Prisma는 같은 SQL을 prepared statement로 재사용한다. PostgreSQL은 custom plan으로 5회 실행한 뒤 generic plan으로 바꿨다(`pg_prepared_statements.generic_plans = 2`).
- generic plan은 검색어를 모르고 결과를 500행으로 가정한다. 그래서 늘 trigram 인덱스를 쓴다.
- 2글자 검색어('카페')는 trigram으로 거를 수 없어서, 인덱스가 **100,023행을 후보로 돌려주고 83,240행을 재검사에서 버렸다**. 그 결과 **222.8ms**가 걸렸다. 값을 보고 세운 custom plan(순차 스캔)은 126~137ms다.
- 3글자 이상('한밭수목원')은 generic plan에서도 30.8ms로 문제가 없었다.
- 03 문서 §9에서 [미검증]으로 남긴 "generic plan은 측정하지 않았다"가 여기서 확인됐다.

**운영 접속 방식에서는? — 접속 설정만 바꾼 A/B** (scale 1, base·head 같은 코드)

| | 직접 접속(이름 있는 statement) | `pgbouncer=true`(운영, 이름 없는 statement) |
|---|---|---|
| 흔한 검색어 p95 | 240.2ms | **152.7ms (-36%)** — 매번 custom plan |
| 그 외 엔드포인트 p95 | 5.4~18.9ms | **+30~96%(+2~8ms)** — 매번 Parse·계획 수립 |

운영(트랜잭션 풀러 + `pgbouncer=true`)은 이 문제를 이미 피하고 있고, 대신 모든 쿼리가 계획 비용을 낸다 [측정].
**직접 접속 구성(로컬 개발, 풀러 없이 배포하는 경우)에서만** 검색 count가 generic plan으로 약 90ms를 더 쓴다.

**수정 — 검색 count 하나만 custom plan 강제** (`backend/src/routes/posts.ts`의 `countSearchResults`)
- `prisma.$transaction([SET LOCAL plan_cache_mode = force_custom_plan, count])`로 바꿨다.
- `SET LOCAL`이라 그 트랜잭션에만 적용되고, 트랜잭션 모드 풀러에서도 다른 클라이언트로 새지 않는다(08 §5의 세션 상태 누수와 대비).
- 다른 쿼리는 계획 캐시를 그대로 쓴다.

| 수정 전 → 후 | 직접 접속 | `pgbouncer=true` |
|---|---|---|
| 흔한 검색어 p95 | **245.2 → 154.8ms (-37%)** | 155.5 → 156.1ms (+0%) |
| 드문 검색어 p95 | 6.6 → 10.4ms (+3.8ms, 트랜잭션 왕복 추가) | 16.1 → 15.6ms |
| 그 외 | 잡음 범위(±18% 이내) | 잡음 범위(±11% 이내) |

드문 검색어 +3.8ms를 내고 흔한 검색어 -90ms를 얻는 교환이다. 운영 방식에서는 중립이다.
`plan_cache_mode`를 DB나 역할 전체에 거는 방법도 있지만, 그러면 모든 쿼리가 계획 비용을 낸다. 위 표에서 그 비용은 +30~96%였다. 그래서 문제 쿼리 하나에만 걸었다.

## 8. 재현 방법

```bash
cd backend && npm run db:test:up                       # 127.0.0.1:54329
bash scripts/load/perf-gate.sh                         # head 단독(절대 기준) — k6가 없으면 grafana/k6 컨테이너 사용
SCALE=1 BASE_DIR=/다른/작업트리/backend bash scripts/load/perf-gate.sh   # base와 비교
SCALE=1 BASE_DIR=$PWD bash scripts/load/perf-gate.sh   # A/A
SCALE=1 BASE_DIR=$PWD BASE_DB_PARAMS= HEAD_DB_PARAMS=pgbouncer=true bash scripts/load/perf-gate.sh   # 접속 설정 A/B
# 결과: backend/perf-out/report.md, {base,head}-N.json, server-*.log
```
