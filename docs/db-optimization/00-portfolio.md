# 백엔드·DB 신뢰성 작업 요약 (개인 포크, 2026-11)

> 대전 여행 PWA "대저니유"(Express 4 + Prisma 6 + PostgreSQL 16)의 백엔드를 **정합성 → 성능 → 운영** 순서로 다시 점검한 기록이다.
> 모든 수치는 로컬 PostgreSQL 16과 고정 시드 합성 데이터(게시물 10만 건 등)에서 직접 잰 값이다. 운영 DB와 실제 사용자 데이터는 쓰지 않았다.
> 상세 문서는 같은 폴더의 01~11이다. 문서마다 **[측정]**·**[추정]**·**[미검증]**을 구분해 적었다.

## 대표 사례 5개

### 1. 동시 요청이 실패하고 교착되던 담기 기능 (02)
- **문제**: 같은 글을 동시에 담으면 대부분 409가 났다. "담기 취소"와 "코스 삭제"가 겹치면 교착이 생겼다.
- **원인 확인**: 통합 테스트(실제 PostgreSQL)로 경합을 재현하고, 서버 로그의 `deadlock detected`에서 두 트랜잭션의 잠금 순서가 반대인 것을 확인했다. mock 단위 테스트로는 잡을 수 없는 문제였다.
- **해결**:
  - 유니크 제약을 경합의 판정자로 쓰고, 진 쪽은 이긴 쪽의 결과를 돌려준다(멱등 처리).
  - 잠금 순서를 `Course → 하위 테이블`로 통일했다.
  - `Post.saves`는 앱이 아니라 DB 트리거가 유지한다. CASCADE 삭제에서도 수가 어긋나지 않는다.
- **결과**: 각 시나리오를 20회 반복한 통합 테스트에서 실패 0, 교착 0이었다.

### 2. 검색이 느렸던 진짜 이유는 인덱스만이 아니었다 (03)
- 10만 건에서 검색 API가 650~720ms 걸렸다. 실행계획을 보니 원인이 세 가지 겹쳐 있었다.
  - 여러 컬럼에 대한 ILIKE
  - 비용 과대 추정으로 켜진 **JIT 컴파일**(쿼리당 약 300ms)
  - 태그 조건의 행 수 과대 추정(결과 없는 검색에 158ms)
- **해결**: 검색 문서 컬럼과 pg_trgm GIN 인덱스, 커서에 선행 범위 조건을 추가했다.
- **함께 고친 기존 버그**: LIKE 와일드카드(`%`, `_`)가 이스케이프되지 않던 문제다.
- **의도적으로 받아들인 대가**: `saves` 인덱스 때문에 담기 UPDATE가 HOT이 안 된다(쓰기 처리량 약 -17%).

### 3. 안전망을 실제로 시험하기 — 백업, 복제, 알림 (06·07·09)
"설정했다"가 아니라 "사고를 일으켜 보니 어떻게 됐다"로 확인했다.
- **PITR**: 시각 기반 복구가 한 번 실패했다. 컨테이너 시계가 약 27초마다 3.7초씩 거꾸로 가는 것을 관측해 원인을 찾았다. 이후 pg_waldump로 사고 트랜잭션 번호(xid)를 특정해 복구하는 절차로 바꿨다.
- **장애 전환**: 비동기 복제에서는 "성공 응답을 받은 커밋"이 실제로 사라졌다(10회 중 2회). 동기 복제는 유실이 없었지만, 대신 응답 없이 반영된 쓰기가 생겼다. 그래서 클라이언트 재시도는 멱등해야 한다.
- **알림**: 장애 6종을 주입하자 3종이 감지되지 않았다. 원인은 셋이었다.
  - exporter 내장 지표의 의미 오해
  - 명령줄 설정이라 `ALTER SYSTEM`이 무시되어 장애 주입 자체가 실패함
  - **DB가 죽으면 수집 자체가 실패해 "DB 다운" 알림이 울리지 않는 사각지대**

### 4. 성능 게이트가 회귀를 놓친 이유 (10)
- PR마다 base·head를 같은 러너에서 번갈아 측정하는 k6 게이트를 만들었다. 같은 코드끼리 비교(A/A)해 잡음 폭을 재고, 판정 기준을 "+25% 그리고 +5ms"로 정했다.
- 검증하려고 trigram 인덱스를 일부러 지웠는데, 게이트가 **두 번 통과시켰다**.
  - 1만 건 데이터에서는 플래너가 원래 인덱스를 거의 안 썼다.
  - 실행계획이 다른 두 종류의 검색이 p95 하나에 섞여 회귀가 묻혔다.
  - 데이터 규모와 집계 단위를 고친 뒤에는 44배 회귀를 검출했다.
- 이 과정에서 **Prisma의 prepared statement가 generic plan으로 바뀌어 2글자 검색이 126 → 223ms**가 되는 문제를 찾았다.
  - 운영 접속(`pgbouncer=true`)은 원래 이 문제를 피한다는 것을 접속 설정만 바꾼 A/B로 확인했다.
  - 직접 접속 구성을 위해 문제 쿼리 하나에만 custom plan을 강제했다.

### 5. 캐시는 성능 장치이지 장애 지점이 아니어야 한다 (11)
- 가장 느린 경로(검색 건수)만 Redis로 공유 캐시했다. Redis가 죽거나 50ms 안에 응답하지 않으면 원본을 직접 읽는다.
- 검색어별 키가 수천 개여도 **세대 번호 INCR 한 번**으로 무효화한다.
- 결과:
  - 메모리 캐시는 서버 2대 중 한쪽이 최대 60초 옛 건수를 보였다. Redis는 즉시 일치했다.
  - 부하 중 Redis를 16초 내려도 실패율은 0%였다.

## 일하는 방식

- **재현 → 원인의 증거 → 수정 → 같은 방법으로 재측정.** 수치는 모두 다시 돌릴 수 있는 스크립트로 남겼다(`backend/scripts/perf`, `scripts/load`, `ops-lab/scripts`).
- **틀린 가설도 기록했다.** 몇 가지 예:
  - "풀러 경유 마이그레이션은 실패할 것" → 실제로는 성공하지만 잠금이 새어 다음 배포를 막았다.
  - "GIN pending list가 검색을 느리게 할 것" → 통제 실험에서 4ms 차이로 기각했다.
- **안전장치를 코드에 넣었다.** 통합 테스트·시드·부하 스크립트는 접속 대상이 로컬이 아니면 시작하지 않는다. 앱용 최소 권한 DB 역할 스크립트도 만들었다.
- **기존 동작을 지켰다.** 기존 마이그레이션은 수정하지 않았고 프론트 API 응답 형식도 유지했다. 동작이 바뀌는 곳(후기 페이지네이션 등)은 프론트와 테스트를 함께 바꿨다.

## 기술

PostgreSQL 16(트리거, pg_trgm, pg_stat_statements, EXPLAIN, WAL 아카이빙·PITR, 스트리밍 복제) · Prisma 6 · Express 4 · PgBouncer ·
Prometheus·Alertmanager·Grafana·postgres_exporter · k6 · Redis(ioredis) · Docker Compose · GitHub Actions · Vitest(단위 107, 통합 31)

## 한계 (솔직하게)

- 운영(Supabase·Railway) 환경에는 적용하거나 측정하지 않았다. 원본 팀 저장소의 배포이기 때문이다. 운영에 반영하기 전 확인할 목록은 05 문서에 있다.
- 측정은 한 대의 PC에서 했다(앱·DB·부하 도구가 같은 호스트). 절대값보다 **같은 조건에서의 전후 비교**에 의미가 있다.
- 2글자 검색어 건수(약 120~150ms)는 남았다. pg_bigm이나 건수 상한 표시는 화면 동작이 바뀌어 보류했다.
