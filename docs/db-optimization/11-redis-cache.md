# 11. Redis 캐시 — 공유 캐시, 세대 무효화, 장애 시 원본 폴백

> 실습일 2026-11-09 · Redis 7.2(로컬 컨테이너, 영속화 없음, 64MB LRU) · ioredis 5 · 측정: 10번 성능 게이트(scale 1, 합성 데이터 10만 건)
> · 표기: **[측정]** · **[추정]**

## 1. 왜, 무엇을 캐시하나

- 10번 게이트에서 가장 느린 경로는 **흔한 검색어의 건수(count)** 였다. 결과가 많아 10만 행 순차 스캔이고, 부하 중 p95가 약 150ms다.
- 목록 자체는 인덱스로 0.1ms라 캐시할 이유가 없다.
- 기존 캐시는 프로세스 메모리였다. 인스턴스가 2대 이상이면 **글쓰기 직후 인스턴스마다 다른 건수**를 보여 준다(§4에서 재현).

캐시 대상은 "몇 초 늦어도 되는 값"으로 한정했다. 건수는 화면의 "총 N개" 표시용이다. 정합성이 필요한 값(담기 상태, `saves`)은 캐시하지 않는다.

## 2. 설계 (`backend/src/lib/cache.ts`)

| 결정 | 이유 |
|---|---|
| `REDIS_URL`이 있으면 Redis, 없으면 메모리 — API(`cached`)는 그대로 | 기존 호출부 23곳 무수정, 로컬 개발은 Redis 없이 동작 |
| **Redis 장애 시 원본 폴백**: 오프라인 큐 끔, 명령 제한 50ms | 캐시는 성능 장치다. 캐시 장애가 서비스 장애가 되면 안 된다 |
| **세대(generation) 키**: `posts:count:{세대}:q:{검색어}`, 글 생성·수정·삭제 시 `INCR` | 검색어별 키가 수천 개여도 무효화는 명령 1번. 옛 키는 TTL로 사라진다 |
| 세대를 못 읽으면(Redis 장애) 캐시를 건너뛰고 바로 센다 | 어느 세대인지 모르면 옛 값을 줄 수 있다 |
| single-flight(프로세스 단위) | 만료 순간 같은 키에 몰린 요청이 count를 동시에 여러 번 돌리지 않게 |
| TTL ±10% 지터 | 같이 채워진 키가 같이 만료되지 않게 |
| 내 글 검색(`mine`)·유형 필터 건수는 캐시 안 함 | 사용자마다·조건마다 달라 적중률이 낮다 |

## 3. 효과 — 게이트(base: 캐시 없음, head: Redis) [측정]

| 엔드포인트 | 3라운드 | 5라운드 |
|---|---|---|
| search_common p95 | 142.7 → **13.1ms (-91%)** | 149.6 → **14.1ms (-91%)** |
| feed 첫 페이지 p95 | +19~24% (+1.5~1.9ms) | +16~26% (+1.6~2.7ms) |
| save p95 | +27%(+5.7ms) → **게이트 실패** | +10% → 통과 |
| 그 외 | 잡음 범위 | 잡음 범위 |

- **save의 3라운드 실패는 잡음으로 판단했다 [추정].** save 경로는 캐시를 쓰지 않는다. head 1·2라운드는 모든 엔드포인트가 함께 느렸고 3라운드는 base와 같았다. 5라운드에서는 통과했다. 같은 PC에서 Redis 컨테이너가 CPU를 나눠 쓰는 영향일 수 있다. 3라운드 게이트가 이런 오탐을 낼 수 있다는 근거이기도 하다.
- **첫 페이지의 +2ms는 실제 비용이다.** 메모리 캐시(0 왕복)를 Redis 왕복 2번(세대 + 값)으로 바꾼 값이다. 공유 캐시의 대가이며, 줄이려면 세대를 로컬에 짧게 들고 있는 2단 캐시를 쓰는 방법이 있다(미적용).
- head의 search_common 라운드 범위는 9.3~148.2ms였다. 60초 TTL로 측정 구간 중 키가 만료되면 다시 셀 때 150ms가 걸린다. 미스 비율이 5% 근처라 p95가 그 경계에 걸린다.
- **적중률은 낙관적이다 [추정].** 부하 시나리오의 흔한 검색어가 10개뿐이어서다. 실제 검색어는 롱테일이라 효과가 이보다 작다. Redis의 `keyspace_misses`에는 아직 없는 세대 키 조회도 포함돼, 적중률 지표로 쓰지 않았다.

## 4. 인스턴스 2대 일관성 — 메모리 vs Redis [측정]

`scripts/load/cache-consistency.sh`로 측정했다. 서버 A·B를 띄우고, B가 '카페' 건수를 캐시한 상태에서 A로 글을 쓰고 바로 B를 조회했다.

| | B: 글쓰기 전 → 직후 | A가 보는 값 |
|---|---|---|
| 메모리 캐시 | 1704 → **1704 (최대 60초 옛 값)** | 1705 |
| Redis + 세대 | 1704 → **1705 (즉시)** | 1705 |

## 5. Redis 장애 주입 [측정]

부하(약 70 요청/초)를 거는 도중 측정 구간 15초째에 `docker stop -t 0`으로 Redis를 내리고, 16초 뒤 다시 올렸다.
- **실패율 0%**, 요청 누락 0이었다.
- 장애 동안은 원본을 직접 읽어서 search_common p95가 155.8ms(캐시 없는 수준)가 됐다. 흔한 검색어 중앙값은 9.9ms로 유지됐다.
- 서버 로그 경고는 10초에 1번으로 제한돼 3줄이었다.
- 재시작 뒤 ioredis가 자동 재연결했고 캐시가 다시 채워졌다(키 16개).

처음에는 장애를 시드 단계(부하 전)에 주입해 무효였다. 서버가 뜬 시점을 기준으로 다시 잡았다.

## 7. 한계

- 프로세스 간 stampede 방지(분산 락)는 넣지 않았다. 인스턴스 N대면 만료 순간 같은 키가 최대 N번 계산된다. 이 서비스 규모에서는 허용 범위로 판단했다 [추정].
- 운영 무료 관리형 Redis(Upstash 등)는 네트워크 왕복이 생겨, 첫 페이지 비용이 위 +2ms보다 커질 수 있다 [미검증].
- CI 게이트에는 Redis를 넣지 않았다. 기본 구성(메모리)으로 측정한다.
